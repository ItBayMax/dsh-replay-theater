# dsh-replay-theater：项目目的与架构

> 基线：`dsh@0.1.2-alpha.2`（上游 commit `0a53fb5`）· 本文档随实现推进更新

## 一、项目目的

**在 DeepSeek Harness 的 Web UI 里，按原始 token 节奏重演一次会话。**

不是"把日志排成时间线"，而是**重演**：play / pause / 单步 / 倍速 / 拖拽跳转，助手的回答像当时那样一个 token 一个 token 地长出来。

### 为什么这件事成立：数据早就在那里

上游把每个 token 的真实毫秒间隔完整保留在日志里：

```ts
// deepseek-harness/packages/core/session/src/chunk-rows.ts:44
/** Epoch-ms gaps between consecutive members; length is one less than the member count. */
dt: number[]
```

同文件 `:48` 写明了这份保留的用意：

> *"one entry per member, never joined — **token boundaries are data**"*

也就是说：token 边界与节奏是上游刻意保护的数据（打包存储时**不合并**成一个字符串），而**至今没有任何东西在使用它**。本插件就是那个使用者。

### 与已有方案的差异

社区已有 4 个回放类尝试（`zoahdev/dsh-replay` 等），全部 ≤4★ 且停更于 2026-08 中旬。差异不在"谁做得更细"，而在形态：

| | 已有方案 | 本项目 |
|---|---|---|
| 载体 | **站外**：解 `session.jsonl.zstd` → 导出自包含 HTML | **站内**：Web UI 的一个标签页 |
| 交互 | 静态时间线（少数带 diff） | **播放控制**（暂停/单步/倍速/跳转） |
| 节奏 | 无（按顺序排列） | **按 `dt[]` 还原真实打字节奏** |
| 用途 | 事后取证 | 观察、教学、演示（可录 GIF） |

已有方案的 packed-row 解码器（处理连接式 Zstd 帧）解决了最脏的活，本项目不重造——离线模式若实现，沿用同一思路。

## 二、架构

### 数据来源

```text
【站内模式 · 主线】
ctx.sessions.binding(sessionId).session
  └─ session.eventSource : ObservableSnapshot<SessionEventWindow>
       └─ entries: HistoryRecord[]
            ├─ { type: 'event',  event: ScalarEvent }    ← 标量事件（block-start/finish/tool-call…）
            └─ { type: 'chunks', event: ChunkRowEvent }  ← 打包运行：texts[] + dt[]  ★节奏数据
  └─ session.loadOlder()  ← 唯一的向前翻页方式

【离线模式 · v2】
session.jsonl 行 → JSON.parse → 展开 text-chunks/reasoning-chunks/tool-call-chunks
```

**一个必须分清的陷阱**：客户端 wire record 与 JSONL 存储行**形状不同**——
- 客户端：外层 `{ type: 'chunks' }`，内层 `{ type: 'chunkrow/text-chunks' }`
- JSONL：直接 `{ type: 'text-chunks' }`

两者语义相同、字段布局相同，但判别符不同。本项目的 `core/wire.ts` 只声明客户端形状；离线模式在 v2 里做独立的归一化入口。

### 模块划分（单向依赖）

```text
src/
  host.ts                宿主半侧：刻意为空（纯客户端特性，包结构需要它）
  index.ts               包根导出
  core/                  ★ 零 React、零 dsh 依赖的纯逻辑（可独立单测）
    wire.ts              上游 wire 形状的结构化镜像 + 两个纯函数
    timeline.ts          （P1）records[] → Frame[]
    player.ts            （P2）播放状态机
  client/                浏览器半侧
    dsh.ts               dsh 客户端 API 的最小类型镜像
    locales.ts           中英字典（locale 拥有全部文案）
    index.ts             插件体：注册 conversation.view 槽 + 字典
    TheaterView.tsx      React 外壳
    TheaterControls.tsx  （P2）播放条
    TheaterStage.tsx     （P2）舞台
```

**为什么 `core/` 必须零依赖**——这不是洁癖，是硬约束：

`@deepseek-ai/dsh-api-session-controller`（提供客户端 session 类型的包）**根本没发布到 npm**（2026-08-31 实测：npm 上只有 `dsh-session@0.0.1-rc.1` 等少数包）。如果核心逻辑 `import type` 上游包，这个项目就无法独立安装、无法独立测试。

所以采用**结构化镜像**：`core/wire.ts` 与 `client/dsh.ts` 自持最小类型声明，逐条标注镜像自上游哪个 `file:line`（钉在 commit `0a53fb5`）。代价与还债路径写在下面的"已知取舍"。

### 关键设计决策

| 决策 | 理由 |
|---|---|
| **不做 Conversation target**，只注册 `conversation.view` 槽 | 已核实 `ui-trajectory` 的 `inject` 第一行就是我们要的全部（`ctx.sessions.binding().session`）；它后面取的 target 我们不需要 → 避开 Definition/snapshot builder 整套机器（11 文件 vs 27 文件） |
| **核心零 React** | `timeline`/`player` 是确定性逻辑（给定 records → 给定帧序列），可脱离浏览器单测；React 只做渲染绑定。呼应上游 0.1.2 删 `client/runtime` 的方向 |
| **`dt` 双重钳制** | 上游明说 gap **可能为负**（时钟回拨，chunk-rows.ts:36）；且真实会话的长静默（模型思考几十秒）在回放时是灾难 → 负值归零 + 可配置的长静默压缩上限 |
| **播当前窗口，不追求"从头播"** | 客户端拿不到 `throughSeq`（被 `Omit`，由 binding 注入），只能 `loadOlder()` 向前翻；实测单尾页可达 41 万事件 → 显式"加载更早"按钮让代价可见 |
| **文案从第一行就进字典** | 0.1.2 硬规则：Cordis-free 原子必须传完整本地化文案且**无兜底措辞**（遗漏是类型错误）；本地化文本**永不承载身份** |

## 三、已知取舍

1. **类型是镜像，不是真依赖**。上游发布相关包后，应把 `core/wire.ts` 与 `client/dsh.ts` 换成真 `import type`。因为镜像是结构化兼容的，替换**不需要改任何调用点**。风险是上游改契约时我们不会被编译器提醒——缓解措施是 README 标注适配基线，并在每次上游同步时复查这两个文件。
2. **只依赖公开面**。只用 `session.eventSource` 与 `loadOlder()`，不碰任何内部路径。上游 0.1.2 已经删过一整个 `client/runtime` 包，所以"只吃公开 API"是生存策略。
3. **MVP 不复刻工具卡**。工具调用在舞台上显示占位 + 名称，不复刻 `ui-tool` 的完整卡片体系（那会牵入大量依赖，且卡片本身不是"节奏回放"的价值所在）。

## 四、阶段计划

| 阶段 | 交付 | 状态 |
|---|---|---|
| **P0** | 包骨架、类型镜像、字典、插件体挂上 `conversation.view`、typecheck 通过 | ✅ 完成 |
| **P1** | `core/timeline.ts` 建帧 + 单测（喂上游官方录制语料） | 待做 |
| **P2** | `core/player.ts` 状态机 + 舞台/播放条组件 | 待做 |
| **P3** | 长静默压缩可调、跳转、工具卡占位、中英文案接线 | 待做 |
| **v2** | 离线模式（拖入 jsonl）+ **并排双轨对比** | 待做 |

`buildTimeline()` 从第一天就设计成接受**任意** records 数组（不绑定"当前会话"），因为 v2 的并排对比正是未来评测插件的核心 UI。
