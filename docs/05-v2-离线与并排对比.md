## 一、离线模式：两种形状的归一化

这是 v2 最容易写错的地方，也是设计文档提前标出的陷阱：**JSONL 存储行与客户端 wire record 不是同一种形状**。

| | 存储行（`jsonl.ts` 的输入） | 客户端 wire record |
|---|---|---|
| 打包 | `{ type: 'text-chunks', … }` | `{ type: 'chunks', event: { type: 'chunkrow/text-chunks', … } }` |
| 标量 | 事件本身 | `{ type: 'event', event }` |

`parseSessionLog()` 做的就是识别 + 抬升（lift）：把存储形状抬成 wire 形状，于是 `buildTimeline()` 一行不改就同时服务两条路径。

### 三个诚实处理

1. **归一化日志没有时间戳也要能播**：上游快照语料剥掉了 `seq`/`time`（`snapshots/AGENTS.md`）。解析器给它们赋行序号 + 合成时钟，但**如实上报 `synthesizedTimes: true`**，UI 显示"该日志没有时间戳——节奏是均匀的，不是原始节奏"。**不假装那是真实节奏。**
2. **打包行要占掉它代表的所有序号**：一个 3 成员的打包行占 seq 1..3，后面的标量必须落到 4。有专门测试守着（否则时间线排序会错乱）。
3. **坏行报告而不是静默丢弃**：解析结果带 `skipped: [{ line, reason }]`，区分"不是 JSON"/"不是对象"/"没有事件类型"/"畸形打包行"。上游把畸形打包行当**损坏存储**而非事件（`chunk-rows.ts:357`），我们沿用这个判断。

## 二、并排对比：分歧检测的关键设计

```ts
findDivergence(left: Timeline, right: Timeline): Divergence
```

### 比什么、不比什么

**刻意不比时间与序号。** 同一个任务跑两次，墙钟不同、序号编排不同——把这些纳入比较会导致**每一对都报分歧**。所以可比身份只取"模型产出了什么、顺序如何"：

```ts
return payload.kind === 'marker'
  ? { kind: 'marker', text: payload.event.type }
  : { kind: payload.kind, text: payload.text }
```

有专门测试守着这条：把右侧的 seq 挪到 9000、time 挪后 5000 秒、dt 改成 999，结果仍然是 `identical`。

### 五种分歧原因

| reason | 含义 |
|---|---|
| `text` | 同类载荷、文字不同（最常见：模型说了不一样的话） |
| `payload-kind` | 一侧在推理、另一侧在正文 |
| `marker-type` | 事件流不同（一侧调了工具、另一侧没调） |
| `left-ended` / `right-ended` | 共享前缀一致，但一侧更长 |

分歧结果携带**两侧的 seek 坐标**（`leftAtMs` / `rightAtMs`），所以"跳到分歧点"能把两个播放头同时送到位——这是给评测用的关键能力。

### 为什么这是评测插件的 MVP

`findDivergence` + `summarize` 已经能回答评测的核心问题：两次运行**在哪一步开始不一样**、各自产出了什么文本/推理/用了哪些工具。它们工作在 `Timeline` 上而不是会话上，所以实时窗口、离线文件、未来的评测报告三条路径共用同一套逻辑。

包根现在导出了这两个函数（外加 `buildTimeline`/`parseSessionLog`），**未来的评测插件可以只依赖 `dsh-replay-theater` 而不挂载任何 UI**。

## 三、UI 决策：对比时只有一个时钟

并排模式下，**左侧（实时会话）由播放条驱动，右侧（离线基线）静态显示到末尾**。

理由：两个独立播放头会立刻带来"要不要同步、按谁的时间轴同步、倍速各算还是共用"一连串问题，而对比的核心诉求是"看分歧在哪"，不是"同时看两场演出"。一个时钟 + 一键跳到分歧点，用最小复杂度满足了核心诉求。

若将来确实需要双时钟（例如做"同步播放两个模型的思考过程"演示），`CompareSide` 已经预留了 `playback?` 字段——传入第二个 playback 即可，`CompareView` 无需改造。
